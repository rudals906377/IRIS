## A. 요구사항 이해

### A-1. 만들려는 시스템

> 쇼핑몰에서 고른 **바로 그 상품**(색·무늬·로고·소매 길이·형태 유지)을, 웹캠에 비친 **지금 이 순간의 내 몸**(생성하거나 미리 녹화한 영상이 아님) 위에 **거울처럼 즉시**(움직임이 바로 반영되도록) 입혀 보여주는 시스템.
> 대상 품목은 상의·하의·모자·장갑이며, 목적은 치수 판정이 아니라 시각적 착용감 확인이다.

따라서 성공 조건은 다음 세 가지가 **동시에** 충족되는 것입니다.

1. **동작 보존**: 화면 속 사람의 동작은 카메라가 방금 찍은 실제 동작이어야 한다.
2. **상품 정체성 보존**: "비슷한 옷을 새로 그려내는 것"이 아니라 "선택한 상품을 재현하는 것"이어야 한다.
3. **저지연**: FPS(초당 프레임 수)만 높은 것이 아니라, 움직인 순간부터 화면에 반영되기까지의 **지연 시간(latency)**이 짧아야 한다.

### A-2. 여섯 가지 기술의 구분

| 구분 | 입력 → 출력 | 시간 조건 | 내 목표와의 관계 |
|---|---|---|---|
| 정지 이미지 가상 착용 | 사람 사진 1장 + 옷 사진 → 합성 사진 1장 | 수 초~수 분 걸려도 됨 | 품질 비교 기준이나 "착용 키프레임" 생성용으로만 쓸 수 있음 |
| 오프라인 영상 가상 착용 | 촬영이 끝난 영상 → 처리된 영상 | 영상 전체를 받은 뒤 처리 | 핵심 목표가 아님(촬영 후 처리 방식) |
| 스트리밍 영상 가상 착용 | 들어오는 영상 → 조금 늦게 나오는 영상 | 처리량(FPS)은 높을 수 있지만, 프레임을 묶어서 처리하므로 수백 ms~수 초 지연이 생길 수 있음 | "부드럽지만 과거 동작"이 보일 수 있어 거울 체감과 다름 |
| **저지연 실시간 가상 착용** | 현재 프레임 → 현재 프레임 결과 | 움직임부터 화면까지 약 100 ms 이하(초기 목표) | **핵심 목표** |
| AR 오버레이·메쉬 변형 | 상품 이미지 + 신체 위치 → 변형해서 붙인 결과 | 매우 빠를 수 있음 | 실시간성 확보에 유리함. 다만 "생성형 착용"과는 다름 |
| 생성형 가상 착용 | 사람 + 옷 → 새로 그려낸 착용 모습 | 대개 한 장에 수 초(고성능 GPU 기준) | 자연스러움은 높지만, 지연과 정체성 변형 위험이 큼 |

**AR(메쉬 변형)로 얻을 수 있는 것과 얻을 수 없는 것**

| AR·마스크 합성으로 얻을 수 있는 것 | 얻을 수 없거나 추정에 그치는 것 |
|---|---|
| 상품 픽셀을 그대로 쓰므로 색·무늬·로고가 원본과 같음 | 원단 재질에 따른 실제 주름·처짐(드레이프)을 물리적으로 재현하지 못함 |
| 얼굴·손·배경을 한 픽셀도 바꾸지 않을 수 있음 | 상품 사진에 없는 옆면·뒷면 |
| 매 프레임 계산량이 작아 저지연 가능성이 높음 [추정] | 긴팔을 반팔로 바꿀 때 드러나야 하는 팔 피부(원래 보이지 않던 정보) |
| 실패하는 경우가 예측 가능함(추적 실패 = 옷이 어긋남) | 사이즈 적합성(치수 판정) |
| | 조명과 옷의 상호작용(추정 셰이딩으로 흉내만 가능) |

**생성형 모델로 얻을 수 있는 것과 얻을 수 없는 것**(조사 시점 공개 모델 기준)

- 얻을 수 있는 것: 몸에 맞게 늘어나고 접히는 자연스러운 모습, 조명·그림자, 보이지 않는 부분의 그럴듯한 추정.
- 얻기 어려운 것:
  - 공개 코드와 가중치로 검증된 **100 ms 이하 저지연**.
  - 로고·글자의 정확한 보존.
  - 프레임마다 따로 생성할 때의 깜빡임 없는 일관성.
  - Mac에서의 실시간 실행.

## B. 현재 조건에서의 결론

### B-1. 한 문단 결론

- **최신 공개 모델만으로 "맥북에서 30 FPS, 100 ms 이하"를 만족하는 생성형 착용을 구현할 수 있다는 근거는 찾지 못했습니다.**
- 공개된 이미지 착용 모델은 확산(diffusion) 모델입니다. 노이즈를 여러 단계에 걸쳐 걷어내며 그림을 만드는 방식이라, 코드 기본값이 20~50단계입니다. 그리고 대부분의 코드는 NVIDIA 전용 설정(CUDA)으로 작성되어 있습니다 [코드].
- 영상용 모델도 거의 모두 오프라인 방식입니다. 유일하게 "실시간 스트리밍"을 표방한 LiveVVT조차 코드가 공개되지 않았고, 발표 수치도 첫 결과까지 1.56초, 갱신당 약 0.5초 수준입니다 [요약].
- 따라서 이 프로젝트의 실시간 핵심은 **"추적 + 마스크 + 변형 + 레이어 합성"을 조합한 마스크 기반 영상합성 파이프라인**으로 맥북에서 직접 구현하는 것이 가장 근거 있는 방향입니다.
- 생성형 모델은 **매 프레임 경로 밖에서**만 씁니다. 상품을 바꿀 때 한 번 "착용 키프레임"을 만들거나, 품질 비교 기준으로 쓰는 역할입니다.
- 추가 GPU는 이 보조 역할을 빠르게 해줄 뿐, 실시간 루프의 가능성 자체를 바꾸지는 않습니다.

### B-2. 조건별 결론

| 범위 | 전제조건 | 판단 |
|---|---|---|
| **맥북 단독으로 근거 있게 시도할 수 있는 범위** | ① MediaPipe 등 추적 모델이 M5에서 수십 ms 이하로 동작 ② 분할(segmentation) 모델 지연을 격프레임 실행이나 저해상도로 감당 ③ 선풍기 없는 설계(팬리스)에서 장시간 성능 유지 | 상의·모자의 **AR 기반 마스크 합성 실시간 착용**은 시도할 근거가 충분함 [추정]. MediaPipe 모델의 모바일 지연 수치를 보면 추적 자체는 수십 ms 수준 [요약]. 가장 큰 위험은 **다중 클래스 분할 모델**(Pixel 6 CPU 217 ms / GPU 71 ms [요약])이며 **1주차 측정으로 확인**해야 함 |
| 맥북에서 생성형 모델 | ① CUDA로 고정된 코드를 MPS(애플 GPU용 PyTorch 백엔드)로 수정 ② DensePose 같은 CUDA 전용 전처리를 자체 마스크로 대체 ③ 메모리가 충분할 것 | **매 프레임 실시간은 근거 없음.** 상품 변경 시 1회 키프레임 생성은 "수십 초~수 분"이 걸릴 가능성 [추정]. 이식에 걸리는 시간을 제한(time-box)해서 시도 |
| 학교 NVIDIA GPU가 있을 때 달라지는 범위 | GPU 메모리(VRAM), 설치 권한, 원격 접속 가능 여부 | 생성형 키프레임을 수 초 단위로 만들 수 있게 됨 [추정]. 프레임 단위 학습형 모델(DM-VTON 계열) 실험 가능. **실시간 루프는 여전히 맥북 로컬이 유리함** |
| 클라우드 GPU가 있을 때 | 예산, GPU 할당 승인, 서울 리전, 동의 절차 | 학교 GPU와 같은 역할 + 네트워크 변동·비용·개인정보 부담. **비동기 키프레임 생성에만 권장** |
| 아직 실험이 필요한 부분 | — | M5 실측 지연, 전신 거리에서의 분할 품질, 팔 교차 시 앞뒤 판단 신뢰도, MPS 이식 가능성, 생성형 키프레임의 로고 보존, 30분 이상 연속 실행 시 발열·지연 누적 |

### B-3. 경로 A·B·C 비교

#### 경로 A: MacBook Air M5 단독

**하드웨어 사실**:
- 2026-03-03 발표, 10코어 CPU, 최대 10코어 GPU(코어마다 Neural Accelerator 탑재), 16코어 Neural Engine, 메모리 대역폭 153 GB/s [요약].
- 통합 메모리 16 GB 기본, 24/32 GB 선택 가능. 팬리스 설계 [요약].
- 기본 13인치 모델은 8코어 GPU일 수 있음 [요약]. **사용자 기기의 메모리와 GPU 코어 수는 미확인**입니다.

**맥에서 실행 가능성 관련 사실**:
- **MediaPipe Python의 macOS GPU 가속은 지원되지 않습니다.** `BaseOptions` 문서 문자열에 "GPU support is currently limited to Ubuntu platforms"라고 적혀 있습니다 [코드]. 즉 Python에서는 CPU로만 추론합니다.
- 최신 macOS용 MediaPipe는 Apple Silicon 전용이며, 예전 `mp.solutions` API가 빠지고 **Tasks API만** 쓸 수 있습니다(0.10.30 이후, 현재 1.0.1) [코드].
- MediaPipe **웹(JavaScript) 버전은 WebGL GPU 가속을 지원**합니다 [코드]. WebGPU 지원 요청은 아직 열려 있습니다 [코드].
- PyTorch MPS: macOS 14 이상에서 동작합니다. 지원되지 않는 연산은 `PYTORCH_ENABLE_MPS_FALLBACK=1`로 CPU에서 대신 실행할 수 있지만, 그만큼 느려집니다 [코드].
- 조사한 생성형 착용 모델 중 **공식적으로 Mac(MPS/Core ML)을 지원한다고 밝힌 것은 없습니다**. AnyDoor·CatVTON·OmniTry 모두 코드에 `cuda`가 고정되어 있습니다 [코드].

**구현 방식 비교**(특정 프레임워크를 먼저 정하지 않음)

| 방식 | 장점 | 단점·위험 | 적합한 역할 |
|---|---|---|---|
| **로컬 Python** (OpenCV + MediaPipe Tasks + PyTorch) | 실험 속도가 빠름. 생성형 모델·측정 코드와 바로 연결됨 | MediaPipe가 macOS에서 CPU로만 동작 [코드]. 화면 출력(`imshow`) 경로의 지연 [미확인] | 1~2주차 측정·실험. 상품 전처리. 생성형 키프레임 |
| **브라우저** (TypeScript + MediaPipe Tasks Vision + WebGL) | MediaPipe GPU 가속 가능 [코드]. 메쉬 텍스처 렌더링이 쉬움. 쇼핑몰·확장 프로그램 연결이 자연스러움 | 브라우저 카메라 경로의 지연 [미확인]. 무거운 모델은 로컬 서버가 필요하므로 구성 요소가 둘로 나뉨 | 실시간 착용 화면(후보) |
| **macOS 네이티브** (Swift + AVFoundation + Vision + Metal) | 지연 제어가 가장 세밀함(`alwaysDiscardsLateVideoFrames`로 늦은 프레임 자동 폐기 [문서]). Vision 사람 분할(fast/balanced/accurate) [요약] | Swift·Metal 학습 부담. **Vision에는 머리카락·피부·옷을 나누는 분할이 없음** [요약]. MediaPipe 모델을 쓰려면 변환 작업이 필요함 | 팀에 Swift 경험자가 있을 때만 |

**권장**: 1주차에 **Python과 브라우저 두 방식 모두에서 "카메라 → 화면 그대로 출력(passthrough)" 지연과 추적 지연을 측정**합니다. 각 100줄 안팎의 코드면 충분합니다. 측정 결과로 실시간 화면 쪽 구현 방식을 하나로 정하고, 상품 전처리와 생성형 키프레임은 Python으로 고정합니다. 측정도 하기 전에 한쪽을 확정하지 않습니다.

**숨기지 말아야 할 비용**:
- DM-VTON의 상관(correlation) 계층은 `cupy`로 된 CUDA 전용 연산이라 Mac 이식에는 코드 재작성이 필요합니다 [코드].
- LiveVVT·FashionChameleon 같은 실시간 생성형 모델을 쓰려면 NVIDIA GPU 여러 장 규모의 증류(distillation) 학습이 전제됩니다. 증류는 큰 모델을 작은 모델에 따라 하도록 가르치는 과정입니다. FashionChameleon 학습 스크립트는 GPU 4장 기준입니다 [코드]. **8주 학생 프로젝트에서 재학습은 범위 밖**입니다.

#### 경로 B: 맥북 + 학교 NVIDIA GPU PC

**전체 지연 구성**(각 항목은 측정 대상이며, 여기의 수치는 측정값이 아님):

```
캡처 → (맥) 전처리 → 압축(인코딩) → LAN 전송 → (GPU) 복원(디코딩) → 추론
     → 결과 압축 → LAN 전송 → (맥) 복원 → 합성·표시
```

- **압축**: Apple VideoToolbox 저지연 모드는 720p·30fps에서 기본 모드보다 **최대 100 ms 지연을 줄일 수 있다**고 Apple이 설명합니다 [문서, WWDC21]. 기본 설정으로 압축하면 지연이 크게 늘 수 있다는 뜻입니다. LAN에서는 프레임마다 JPEG로 보내는 방식도 비교 대상입니다.
- **네트워크**: 대규모 측정에서 Wi‑Fi 지연은 꼬리가 깁니다. 90백분위 약 20 ms, 99백분위 약 250 ms로 보고되었습니다 [요약, Sui et al. MobiSys 2016]. **유선 LAN을 권장**합니다.
- **Python WebRTC(aiortc)**는 H.264를 소프트웨어(libx264)로 압축하며 하드웨어 인코더를 쓰지 않습니다 [코드]. 지연 예산에 이 점을 반영해야 합니다.

**핵심 판단**: 권장 구조에서는 GPU가 **매 프레임 경로 밖**(비동기 키프레임 생성)에 있습니다. 그래서 네트워크 지연이 "움직임 → 화면 지연"에 영향을 주지 않고, "고품질 모드가 준비되기까지 걸리는 시간"에만 영향을 줍니다. 경로 B를 **매 프레임 경로**에 넣는 경우는 학습형 프레임 단위 모델(DM-VTON 계열) 연구 실험뿐입니다.

**GPU PC에 웹캠과 모니터를 직접 연결하는 구성**:
- 네트워크 왕복 구간이 사라져, 매 프레임 GPU 모델을 실험할 때는 이쪽이 유리합니다 [추정].
- 대신 발표 장소가 GPU PC가 있는 곳으로 고정됩니다.
- MediaPipe Python의 GPU 가속은 Ubuntu에서만 됩니다 [코드]. 따라서 GPU PC의 OS도 확인해야 합니다.

**학교 GPU 메모리 조건별 가능 범위**:

| GPU 메모리 | 가능해지는 실험 |
|---|---|
| 8 GB 이상 | CatVTON("1024×768에서 8 GB 미만", bf16) [코드] |
| 약 18~24 GB 이상 | AnyDoor. 제3자 논문에서 18 GB 사용 보고, 장비는 미상 [요약]. 15.7 GiB GPU에서 메모리 부족 이슈가 있음 [코드] |
| 28 GB 이상 | OmniTry("최소 28 GB", bf16) [코드] |

## D. 최종 권장안과 대안

### D-1. 권장안: 하이브리드 마스크 기반 영상합성

> **실시간 경로(매 프레임, 맥북 로컬)**: 신체 추적 → 교체·보존·가림 마스크 구성 → 부위별 메쉬 변형 → 셰이딩 전이 → 레이어 알파 합성
> **준비 경로(상품 변경 시 1회, 비동기)**: 상품 분리·부위 분할·기준점 + (선택) 생성형 **착용 키프레임**

- **모델 하나로는 부족합니다.** 조사한 어떤 단일 모델도 "실시간 + 상품 정체성 + 4개 품목"을 동시에 충족한다는 근거가 없습니다. 추적(MediaPipe/Vision), 마스크, 변형, 합성을 **조합**해야 합니다.
- **생성형 착용 키프레임이란**: 사용자가 정면 자세를 취한 한 프레임에 CatVTON 등으로 상품을 입힌 이미지를 만들고, 거기서 옷 영역만 잘라 "몸에 맞게 입혀진 텍스처"로 씁니다. 이후 실시간 루프는 이 텍스처를 현재 자세로 변형합니다.
  - 평평한 상품 사진을 변형하는 것보다 **변형 폭이 작고, 몸에 맞는 목선·주름이 이미 반영되어 있다**는 장점이 있습니다 [추정].
  - 비슷한 발상의 연구도 있습니다. LiveVVT도 "정면 착용 키프레임"을 외형 메모리로 쓴다고 합니다 [요약]. 다만 LiveVVT의 구현은 공개되지 않았으므로 직접 근거로 쓰지는 않습니다.
- **정체성 보호 장치**: 키프레임은 로고·색 보존 지표(F-4)를 통과할 때만 채택합니다. 통과하지 못하면 평평한 상품 이미지 텍스처로 자동으로 돌아갑니다. 이렇게 해야 "비슷한 옷 생성"과 "선택한 상품 재현"이 섞이지 않습니다.
- **검증 순서**: ① 평평한 상품 텍스처만으로 실시간 루프 완성(필수) → ② 키프레임 텍스처 추가(목표) → ③ 두 방식을 같은 지표로 비교.

### D-2. 대안(권장안의 생성형 부분이 실패했을 때)

**순수 AR 마스크 합성 + 셰이딩 전이.** 생성형 키프레임을 완전히 빼고, 평평한 상품 이미지 텍스처에 **사용자가 원래 입은 옷의 밝기 변화(주름·그림자)를 곱해** 입체감을 냅니다.

- 적용 조건: 맥에서 이식 실패, 키프레임 생성이 너무 느림(예: 2분 초과), 정체성 지표 미달.
- 실시간 루프는 그대로이므로 **필수 범위는 영향을 받지 않습니다.**

실시간 경로 자체가 느린 경우의 대응은 대안이 아니라 **튜닝 순서**로 정해 둡니다(F-6):
1. 해상도 낮추기
2. 분할을 격프레임으로 실행
3. 실행 방식 교체(Python → 브라우저 또는 네이티브)

### D-3. AnyDoor의 역할

- **주력 모델로는 부적합**합니다.
  - 기본 50단계 확산으로 공식 속도 수치가 없고, 제3자 보고는 7.1초/장입니다 [요약].
  - README 스스로 착용 전용 설계가 없다고 밝힙니다 [코드].
  - CUDA가 고정되어 있습니다 [코드].
- **적절한 역할**:
  1. **비교 기준**: 교수님이 제시한 모델로서, 정지 이미지 품질을 기준으로 삼습니다. 같은 프레임과 상품으로 AnyDoor 결과와 우리 실시간 결과를 나란히 보여주면 "품질 대 지연"의 교환 관계를 설명할 수 있습니다.
  2. **보조 기능**: CatVTON이 지원하지 않는 **모자·장갑** 키프레임을 만드는 실험 도구로 씁니다. AnyDoor는 객체 단위 삽입 모델이라, 머리나 손 영역을 박스·마스크로 지정해 넣을 수 있습니다 [코드]. 품질은 미확인입니다.
- AnyDoor도 **마스크로 교체 영역을 지정하는 모델**입니다. 따라서 "마스크 기반 영상합성"이라는 주제의 연결고리로 발표에 활용할 수 있습니다.

### E-3. 마스크 설계(주제의 핵심)

사용하는 도구가 **실제로 출력하는 신호**만 씁니다.

| 신호 | 제공하는 도구 |
|---|---|
| 관절점과 상대 z | Pose / Hand |
| 사람 마스크 | Pose 옵션 또는 Vision |
| 머리카락·피부·옷 클래스 | 다중 클래스 분할 |
| 머리 자세 | Face |

손 마스크, 옷 1벌 단위 분할, 픽셀 깊이는 **어떤 도구도 제공하지 않습니다.** 따라서 아래처럼 직접 구성합니다.

| 마스크 | 정의 | 만드는 방법 |
|---|---|---|
| **상품 분리 M_prod** | 상품 이미지에서 옷만 남긴 영역 + 부위 레이어 | ③④ 반자동 처리 + 수동 보정. 1회 계산 후 캐시 |
| **착용·교체 M_new** | 새 옷이 그려질 영역 | M_prod를 현재 자세로 변형한 실루엣(메쉬 변형 결과의 알파) |
| **채움 M_fill** | 기존 옷 중 새 옷에 덮이지 않아 **지워야 하는** 부분 | (옷 클래스 ∩ 해당 품목 신체 영역) − M_new. 신체 영역은 관절점으로 만든 캡슐 모양 |
| **보존 M_keep** | 절대 바꾸면 안 되는 영역 | 얼굴 피부 + 머리카락(모자 영역 제외) + 손 + 배경. **합성 결과에서 M_keep 픽셀은 원본과 같아야 함**(자동 검증 가능) |
| **가림 M_occ** | 새 옷보다 **앞에 있는** 신체 | 손: 손 관절점 21점으로 손가락 캡슐 + 손바닥 다각형을 그려 약간 확장. 팔뚝: 팔꿈치–손목 캡슐 + (몸통 영역 안의 몸 피부 픽셀) |

**합성 순서**(레이어 방식):

```
1. 출력 = 현재 카메라 프레임
2. M_fill 영역 = 배경판(몸 윤곽 밖) 또는 추정 피부(몸 윤곽 안)
3. 새 옷 레이어를 뒤에서 앞 순서로 그리기(예: 뒤판 → 몸통 → 소매). 경계는 부드러운 알파
4. M_occ 영역 = 다시 카메라 프레임(손·팔이 옷 앞으로 나옴)
5. 검증: M_keep 영역의 입력과 출력 차이 ≈ 0
```

**셰이딩 전이**:
- 사용자가 원래 입은 옷(밝은 무지 옷 권장)의 밝기를 `L`이라 할 때, `S = L / blur(L)`로 주름·그림자 성분을 뽑습니다. 이것을 새 옷 텍스처에 곱해 실제 몸의 주름과 조명을 흉내 냅니다.
- 휴리스틱일 뿐 물리 시뮬레이션이 아닙니다. 원래 옷이 어둡거나 무늬가 있으면 실패합니다.

### E-4. 프레임 간 갱신

- **관절점 흔들림 제거**: One Euro 필터를 씁니다(Casiez et al., CHI 2012). 느리게 움직일 때는 강하게, 빠르게 움직일 때는 약하게 거르는 필터라, 지연을 적게 더하면서 떨림을 줄입니다.
- **마스크**: 움직임 크기에 따라 가중치를 바꾸는 시간 평균을 씁니다(정지 시 과거 비중 ↑, 움직일 때 현재 비중 ↑). 또 가이드 필터로 경계를 영상의 실제 윤곽에 맞춥니다.
- **느린 분할 결과 보정**: 분할이 1프레임 늦으면, 그 사이 관절점 이동량으로 마스크를 밀어 현재 프레임에 맞춥니다.
- **추적 실패**: 가시성 값이 기준보다 낮으면 마지막 자세를 최대 약 200 ms 유지한 뒤 옷을 서서히 사라지게 합니다. 이 수치는 실험으로 조정합니다. 틀린 위치의 옷을 보여주지 않는 것이 원칙입니다.
- **동기 모드와 비동기 모드**(중요한 설계 선택, 둘 다 측정):
  - **동기 모드**: 자세를 계산한 바로 그 프레임 위에 합성합니다. 옷은 정확히 붙지만, 화면 전체가 파이프라인 지연만큼 늦습니다.
  - **비동기 모드**: 가장 최신 카메라 프레임 위에 직전 자세로 옷을 합성합니다. 몸은 더 즉각적으로 보이지만, 빠르게 움직이면 옷이 미끄러져 보입니다.
  - 선택 사항: 측정된 지연만큼 관절점을 앞질러 예측하는 방법도 실험합니다. 효과와 과잉 반응(overshoot)을 함께 측정합니다.

### E-5. 어려운 상황별 처리

| 상황 | 처리 방법 | 한계(정직하게) |
|---|---|---|
| **팔을 몸 앞에서 교차** | 몸통과 좌우 소매를 별도 레이어로 그림. 손목·팔꿈치의 z가 어깨보다 충분히 앞이고 팔뚝이 몸통 영역과 겹치면, 소매를 몸통 **앞**에 그림. 두 팔끼리의 순서는 손목 z 비교 + 히스테리시스로 결정 | MediaPipe z는 추정값이라 흔들림 [추정]. 1~2주차에 신뢰도를 측정하고, 실패하면 "제한 동작"으로 분류 |
| **손이 상의를 가림** | 손 관절점으로 만든 손 마스크 ∪ (몸통 안의 몸 피부 픽셀)을 M_occ로 사용 → 카메라 원본을 맨 위에 다시 그림 | 소매 없는 옷을 입으면 몸통 피부와 팔을 구분하지 못함 → 데모 복장 규칙으로 해결 |
| **긴팔 → 반팔** | 새 소매 끝부터 손목까지 원래 긴소매가 있던 부분이 M_fill이 됨. 두 가지 방법: ① 데모 복장 규칙(반팔을 입고 시연) ② 얼굴·손에서 추출한 피부색 × 원래 소매의 밝기 변화로 피부 합성(실험) | 실제 팔 피부는 카메라에 없는 정보. 실시간으로 사실적인 복원은 **근거 없음**. 생성형 인페인팅은 키프레임에서만 시도 가능 |
| **넓은 옷 → 좁은 옷** | 원래 옷이 새 옷 밖으로 삐져나온 부분(M_fill) 중 몸 윤곽 **밖**은 **배경판**(세션 시작 시 촬영)으로 채움. 몸 윤곽은 관절점 캡슐 모델로 추정 | 카메라가 움직이거나 조명이 바뀌면 배경판이 어긋남 → 고정 카메라와 배경판 재촬영 기능. 몸 윤곽은 추정값 |
| **좁은 옷 → 넓은 옷** | 새 옷이 덮으므로 쉬움 | — |
| **모자와 머리카락** | 얼굴 변환 행렬로 머리 자세를 구하고, 이마 관절점으로 챙 위치를 잡음. 챙 선 **위**의 머리카락은 모자로 덮음. 모자 실루엣 밖으로 삐져나온 머리카락은 배경판으로 지움. 챙 **아래** 앞머리는 M_keep으로 보존 | 앞면 이미지 1장이라 좌우 회전이 크면 부자연스러움. 단순 3D 형상(타원체)에 텍스처를 입히는 방법은 확장 과제 |
| **장갑: 손가락 굽힘·서로 가림** | 손가락마다 MCP–PIP–DIP–TIP 마디 선을 따라 텍스처 띠를 마디별로 강체 변환. 손가락 간 순서는 손 관절점 z로 결정. 손등·손바닥은 방향으로 판단 | 주먹을 쥐거나 깍지를 끼면 관절점 신뢰도가 떨어짐 → 제한 동작. 상품 사진에 손바닥 면이 없으면 색만 재사용한 **추정** 텍스처 |

### E-6. 상품 사진에 없는 옆면과 뒷면

| 영역 | 처리 | 성격 |

| 60° 이상, 뒤돌기 | 옷을 서서히 사라지게 하거나 경고 표시(데모 제한 동작) | 미지원 |

### E-8. 개인정보 설계

- **원칙**:

  - 기본 설정에서는 저장하지 않습니다.

  - 학생 프로젝트가 법의 "개인정보처리자"에 해당하는지는 미확인입니다. **그래도 동의 절차를 적용합니다.**
- **평가용 녹화**: 참가자에게 서면 동의를 받습니다. 동의서에 담을 항목은 제15조를 따릅니다 [요약]:
  - 목적(성능 평가)
  - 항목(영상)
  - 보관 기간(예: 프로젝트 종료 후 30일 내 삭제)
  - 거부 권리와 불이익
  - 녹화 파일은 암호화된 로컬 폴더에 보관하고, 외부 공유를 금지합니다.
- **외부 GPU로 보내는 경우(경로 B·C)**:
  1. 필요한 영역만 보냅니다. 키프레임 생성에는 몸통이나 해당 부위 크롭이면 충분합니다.
  2. **얼굴 영역은 가리거나 흐리게 한 뒤** 전송합니다(착용 합성에 얼굴이 필요 없음) [추정].
  3. 암호화 전송(TLS, WebRTC DTLS-SRTP)을 씁니다.
  4. 서버는 메모리에서만 처리하고 디스크에 쓰지 않으며, 로그에 이미지를 남기지 않습니다.
  5. 세션이 끝나면 결과를 삭제합니다.
  6. 클라우드는 서울 리전을 씁니다. 국외 리전을 쓰면 국외 이전에 대한 별도 동의가 필요합니다(제28조의8) [요약].

### F-1. 측정 지표 정의

| 지표 | 정의 | 측정 방법 |
|---|---|---|
| 화면 표시 FPS | 화면에 새 프레임이 표시되는 빈도 | 표시 시각 로그 |
| **합성 갱신 빈도** | **새로운 자세·마스크로** 다시 합성된 결과가 나오는 빈도(같은 결과를 반복 표시한 것은 제외) | 결과 프레임 ID 로그 |
| 추적·분할 갱신 빈도 | 관절점과 분할 결과 각각의 갱신 빈도 | 단계별 로그 |
| **움직임 → 화면 지연(motion-to-photon)** | 실제 몸이 움직인 순간부터 화면에 반영되기까지 | **외부 촬영**(F-2) |
| 소프트웨어 파이프라인 지연 | t_cap(캡처 시각) → t_disp(표시 시각) | 프레임별 타임스탬프 |
| 추가 처리 지연 | (착용 켰을 때 지연) − (그대로 출력 기준 지연) | 두 조건 비교 |
| 첫 결과 시간 | 앱 시작 → 첫 합성 / 상품 선택 → 첫 합성(캐시 적중·미적중 구분) / 키프레임 준비 시간 | 이벤트 로그 |
| 지연 누적 | 30~60분 연속 실행 시 분 단위 중앙값의 추세 | 장시간 로그 |
| 순간 지연과 드롭 | p95, p99(상위 5%, 1% 지점), 최댓값, 150 ms 초과 프레임 수, 캡처했지만 표시하지 못한 프레임 비율 | 로그 |

### F-2. 지연을 외부에서 측정하는 방법

1. **스마트폰 슬로모션 촬영(권장, 비용 0원)**:
   - 240 fps 슬로모션으로 **실제 사람(또는 손에 든 LED·플래시)과 노트북 화면을 한 화면에** 담아 촬영합니다.
   - 실제 사건(LED가 켜짐, 손이 기준선을 지남)과 화면 속 반영 사이의 프레임 수를 셉니다. 1프레임은 약 4.2 ms입니다.
   - 동작마다 20회 이상 반복해 중앙값과 p95를 보고합니다.
2. **LED + 포토다이오드 + Arduino**: Bachhuber & Steinbach의 공개 설계로, 정확도 약 0.5 ms, 부품비 50달러 미만입니다 [문서, G2GDelay 저장소].
3. **화면 시계 촬영**: 웹캠으로 밀리초 시계를 찍어 화면 속 시계와 실제 시계의 차이를 봅니다. 값이 흔들리므로 보조 수단으로만 씁니다 [문서].

**반드시 "그대로 출력(passthrough)" 기준 지연부터 잽니다.** 카메라와 화면만으로도 지연이 생기므로(측정 전에는 알 수 없음), 목표는 "기준 지연 + 처리 추가 지연"으로 나누어 관리합니다.

### F-3. 목표치 검토(요구 목표이며 보장된 성능이 아님)

**연구 근거**:
- 전신 가상 거울 연구(Waltemate et al., VRST 2016): **75 ms를 넘으면** 운동 수행과 동시성 지각이 나빠지고, **125 ms를 넘으면** 행위 주체감과 신체 소유감이 떨어졌습니다 [요약].
- VR 거울 속 아바타 지연의 50% 감지 한계는 약 130 ms였습니다(Olimov et al., 2024) [요약].

**판단**: "100 ms 이하"는 거울과 **연결된 느낌**의 합격선으로 타당합니다. 다만 "지연을 느끼지 못함"을 보장하지는 않습니다. 그래서 목표를 세 단계로 나눕니다.

| 단계 | 기준 |
|---|---|
| 필수(합격) | 움직임→화면 지연 **중앙값 100 ms 이하, p95 133 ms 이하**(30 fps 기준 4프레임). 합성 갱신 25 fps 이상을 30분 유지. 지연 누적(마지막 5분 중앙값 − 처음 5분 중앙값) 10 ms 이하 |
| 목표 | 중앙값 **75 ms 이하**. 처리 추가 지연 33 ms 이하 |
| 조명 조건 | 어두우면 카메라가 노출 시간을 늘려 프레임률 자체가 떨어질 수 있음 [추정]. 측정 조명을 고정하고 기록 |

**최신 프레임 우선 정책**:
- 처리 대기열은 1칸으로 두고, 새 프레임이 오면 이전 프레임을 버립니다.
- 느려지면 "밀린 과거 프레임을 차례로 처리"하지 않고 **건너뜁니다.** 부드러움보다 즉시성이 우선이기 때문입니다.
- AVFoundation의 `alwaysDiscardsLateVideoFrames`(기본값 true)가 같은 정책입니다 [문서].

## G. 8주 구현 계획과 최종 데모 범위

### G-1. 범위

| 구분 | 내용 |
|---|---|
| **필수(반드시 완성)** | 상의 단독 실시간 착용(마스크 합성, 손 가림 처리, 셰이딩 전이). 모자 단독. 상품 업로드 + 캐시. 지연·화질 측정 보고서와 측정 영상 |
| **목표** | 하의 단독. 장갑 단독(제한 동작). 상의 + 모자 동시 착용. 생성형 키프레임 "고품질 모드" |
| **확장·연구** | 4개 품목 동시 착용. 브라우저 확장 연동. 뒷면 이미지. GPU 프레임 단위 학습형 모델 비교. LiveVVT 코드 공개 시 비교 |

**품목 순서: 상의 → 모자 → 하의 → 장갑**
- 상의: 주제의 핵심이며 가림과 교체 문제가 모두 들어 있음.
- 모자: 형태가 변하지 않는 물체라 빨리 완성 가능.
- 하의: 전신이 화면에 들어와야 하고, 다리가 교차하며, 상의와의 경계(넣어 입기·빼 입기)가 생김.
- 장갑: 손가락 관절이 많고, 스스로를 가리며, 화면에서 차지하는 픽셀이 적어 가장 어려움.

**동시 착용이 단독 착용보다 어려운 이유**:
- 계산량 증가: 손과 얼굴 추적이 추가됩니다. 착용한 품목의 추적만 켜서 줄입니다.
- 레이어 규칙: 소매와 장갑 중 무엇이 위에 오는지, 상의를 바지 밖으로 뺄지 등을 정해야 합니다.
- 경계 공유: 상의와 하의의 교체 마스크가 허리선을 공유합니다.

→ **단독 착용이 모두 필수 기준을 넘긴 뒤에** 조합합니다.

## H. 교수님께 드리는 프로젝트 방향 제안문

> **제목: 마스크 기반 레이어 합성을 이용한 실시간 웹캠 가상 착용 시스템**
>
> 본 프로젝트는 쇼핑몰 상품 이미지를 웹캠 속 사용자에게 **거울처럼 즉시** 입혀 보이는 것을 목표로 합니다. 제시해 주신 AnyDoor를 비롯해 최신 공개 착용 모델(CatVTON, OmniTry, CatV2TON, LiveVVT 등)을 조사했습니다. 그 결과 이들은 한 장에 수 초 이상 걸리는 확산 모델이거나, 촬영이 끝난 영상을 처리하는 오프라인 방식이거나, 코드가 공개되지 않은 상태였습니다. 따라서 이 모델들을 그대로 쓰면 "움직임 → 화면 100 ms 이하"라는 핵심 요구를 충족할 근거가 없었습니다.
>
> 이에 실시간 처리의 핵심을 **마스크 기반 영상합성 파이프라인**으로 설계했습니다. 신체 추적 결과로 매 프레임 ① 상품 분리 마스크, ② 교체 마스크, ③ 보존 마스크(얼굴·손·배경), ④ 가림 마스크(옷 앞의 손·팔)를 구성합니다. 그런 다음 상품을 부위별로 변형하고 앞뒤 순서에 맞춰 합성합니다. AnyDoor와 같은 생성형 모델은 **상품을 바꿀 때 한 번만 실행**해 몸에 맞는 착용 모습(키프레임)을 만드는 보조 역할과 **품질 비교 기준**으로 활용합니다. 이렇게 하면 생성형 모델의 자연스러움과 마스크 합성의 즉시성·상품 정체성 보존을 함께 활용할 수 있습니다.
>
> 성과는 FPS만이 아니라 **움직임 → 화면 지연(슬로모션 외부 측정), 장시간 지연 누적, 로고·색 보존, 손 가림 실패율** 등으로 정량 평가하겠습니다. 상의를 먼저 완성한 뒤 모자, 하의, 장갑 순으로 확장하겠습니다. 뒤돌기처럼 상품 사진에 없는 정보가 필요한 동작은 제한 사항으로 명확히 밝히겠습니다.

## I. 결론을 바꿀 수 있는 미확인 정보

1. **교수님의 평가 기준**: 생성형 모델(AnyDoor 계열)이 반드시 매 프레임 합성의 **주력**이어야 하는지, 아니면 마스크 합성이 주력이고 생성형이 보조여도 되는지. **권장안 전체가 이 답에 달려 있습니다.**
2. **맥북 사양**: 통합 메모리(16/24/32 GB)와 GPU 코어 수(8/10). 맥에서 생성형 키프레임을 시도할 수 있는지가 달라집니다.
3. **학교 GPU**: 모델명과 VRAM, OS, 설치·원격 접속 권한, 발표장 반입 가능 여부.
4. **클라우드 예산**: 소액이라도 있는지(경로 C 가능 여부).
